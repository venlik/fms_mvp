# ADR-003

# One Application Service Per Use Case

## Status

Accepted

---

## Date

2026-09-18

---

## Context

The Finance Management System's Application layer must orchestrate use cases without violating the Domain's invariants or leaking infrastructure concerns.

Two alternative approaches were considered:

1. One Application Service per Aggregate Root (e.g., `InvoiceService` with many methods)
    
2. One Application Service per business operation cluster (e.g., `InvoiceLifecycleService`, `PaymentService`)
    
3. One Application Service per use case (e.g., `IssueInvoiceService`, `RecordPaymentService`)
    

The system has a well-defined Use Case catalogue in `01-Requirements/common/Use-Cases.md`. Each use case has a stable identifier (`UC-XXX-NNN`) and clear preconditions and postconditions.

---

## Decision

The Application layer SHALL use one Application Service per use case.

Each Application Service SHALL be named after the use case it realizes.

Example:

- `UC-INV-002 — Issue Invoice` → `IssueInvoiceService`
    

Application Services SHALL be small, focused, and independently testable.

---

## Consequences

### Positive

- Direct correspondence with the Use Case catalogue
    
- Small units of application logic
    
- Document Number retries, cross-Aggregate coordination, and transaction boundaries tailored per use case
    
- No god services that accumulate unrelated operations
    
- Easier testing — one test suite per use case
    
- Easier reasoning — a single file answers "what does this use case do?"
    

### Negative

- More files than an aggregate-based organization
    
- Some shared helpers may emerge (e.g., Document Number assignment flow) — these are extracted as supporting concepts, not inherited
    

---

## Alternatives Considered

### One Service per Aggregate Root

Rejected.

Leads to god services. Unrelated operations cluster in the same file. Transaction boundaries become unclear.

### One Service per Business Operation Cluster

Rejected.

The clusters are not defined by the Domain. They drift toward procedural grouping. Documentation and testing become harder.

### Hybrid (Per Aggregate + Per Use Case)

Rejected.

Introduces two organizing principles. Adds ambiguity without benefit.

---

## Notes

- This decision applies to all business modules, not just Billing.
    
- ADR-001 established the DDD + Layered Architecture; this ADR refines the Application layer's structure.
    
- Application Services SHALL NOT implement Business Rules. Business Rules remain in the Domain.
